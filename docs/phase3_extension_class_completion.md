# 第三弾拡張④「初心者教室修了記録」実装前設計メモ

確定日: 2026年8月20日
次回実装の起点として、このメモを起点に着手すること。

## 1. 第三弾と第四弾の責務分担

- 第三弾（bowling-lane-management-system）: 予約・教室運営・グループ単位の出欠・スライド管理
- 第四弾（bowling-lane-growth-system）: 会員本人を基準にした個人情報・投球記録・成長支援・競技者支援
- 第三弾と第四弾は別アプリ・別データベースであり、外部キーによる自動連携は行わない
- 第三弾Userと第四弾User（会員）は別テーブル・別認証システムであり、自動的な紐付け手段は持たない
- 団体参加者を含め、第三弾の教室運営情報と第四弾の会員情報の対応付けは、必要なタイミングでスタッフが手動で行う
- 人数・運用量が増えて手動対応が負担になった段階で、自動連携は将来の拡張候補として検討する（今回は作らない）

## 2. 初心者教室の本来の目的

- ボウリングをスポーツとして理解してもらう
- 基本的な技術やマナーを身につけてもらう
- 教室終了後に、一般ボウラーとして予約・利用できるようにする
- その後、継続して通うか競技者を目指すかは本人の意思に委ねる（教室側から誘導・評価しない）

このスポーツボウリング場自体が「競技者が静かな環境で投げられる場所を作る」という趣旨を持つため、初心者教室は競技者としての適性を判定する場ではない。

## 3. なぜ5回分の個人出席履歴を第四弾には持たないのか

- 初心者教室の4つの目的（上記2.）は、いずれも「修了したかどうか」という1点の事実で判定できる。第何回に出席・欠席したかという粒度の情報を、後から使う具体的な場面がない
- 第四弾がこれまで一貫して持ってきたのは「投球記録」「ギア」「成長ダッシュボード」など、競技者としての"今"を表すデータ。5回分の出欠履歴は教室という一時的なプロセスの記録であり、性質が異なる
- 5回分の個人記録を持つ設計は、第三弾のClassEnrollment一覧を見ながら開催回ごとに手作業で紐付ける必要があり、運用負荷が大きい（修了記録のみなら教室終了時に1回で済む）
- グループ単位の出欠・スライド管理は第三弾側にすでに存在し、教室運営としての役割を引き続き果たすため、個人単位で重複して持つ必要がない

## 4. なぜコーチによる適性評価・修了時総評も持たないのか

- 初心者教室は競技者としての適性を判定する場ではないため、コーチによる評価・総評という概念自体がこのシステムの構想にない
- 継続するか競技者を目指すかは本人の意思であり、コーチ側から評価・誘導する設計にしない
- 指導メモが必要になった場合も、それは教室運営（各回ごとの記録）の領域であり、第三弾側で完結させるべきもの。第四弾を経由する理由がない

## 5. ClassCompletionRecord の確定フィールド

第四弾（bowling-lane-growth-system）側に新設する。

| フィールド | 型 | 説明 |
|---|---|---|
| id | Integer, PK | |
| user_id | Integer, FK → 第四弾User.id | 本物の外部キー。会員本人 |
| external_course_id | Integer | 第三弾ClassCourse.course_id の値。FKではなく参照値のみ（別データベースのため） |
| completed_at | DateTime | 修了日 |
| recorded_by_staff_id | Integer, FK → 第四弾Staff.staff_id | 記録した第四弾スタッフ（監査用） |

- session_number・開催日など、第三弾側で可変な情報は一切コピーしない
- 出席回数、各回の指導内容、コーチによる適性評価・総評は含めない

## 6. 第四弾で管理する事実は1つだけ

第四弾では「初心者教室を修了し、一般ボウラーとして利用可能になった」という事実だけを管理する。
出席回数・各回の指導内容・コーチによる適性評価は一切管理しない。

## 8. 重要な注意（今後の変更について）

今回の設計変更は「機能を削った」のではなく、初心者教室の目的と第四弾の責務に照らして、必要な情報だけに絞った設計判断である。
今後、第三弾側の教室運営機能（グループ出欠・スライド・コーチシフト管理等）を拡張する際に、この設計判断（第四弾は修了事実のみを持つ、という責務分担）を前提の確認なしに変更しないこと。変更が必要になった場合は、あらためて目的に立ち返って再評価すること。
